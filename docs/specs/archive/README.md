# Archive — v1 and earlier

**Nothing here is the current design.** The live specification is
[`../2026-08-28-carb3-site-energy-system-implementation.md`](../2026-08-28-carb3-site-energy-system-implementation.md)
and its four planning companions in [`../`](../).

These documents are archived, **not retired**. v1 remains the COMIT-parity baseline, and the
chain of custody that makes any v2 result defensible runs through it in two hops:

```
   coupled-off COMIT  ──V1──►  v1 spec  ──V1b──►  v2 spec
                               (here)             (live)
```

Neither hop may be skipped, so v1 must stay readable and citable. It just no longer sits in
the main reading path, because v2 §3 is now self-contained and nothing in the live spec
requires you to open v1 to understand it.

## Reading a `§` reference here

**v2's section numbers are deliberately aligned with v1's.** Where both documents define an
entity it sits at the same number in both — §3.11 is `premise_measured_emissions` in each.
Where v2 replaced a v1 entity, the replacement took the original's number: v2's `carrier` is
§3.4 because v1's `commodity` was, and `unit` is §3.5 because `technology` was.

So a `§3.x` reference means the same thing in either document, and the two can be read side
by side without translation. That alignment is load-bearing for V1b and should survive any
future renumbering.

The one place they diverge is §3.3: v1's `activity_process_energy_profile` (a vector split)
became v2's `activity_process_duty_profile` (a duty split). Same slot, same job, different
decomposition — and the v1 table survives as V1b's parity target rather than as an input.
